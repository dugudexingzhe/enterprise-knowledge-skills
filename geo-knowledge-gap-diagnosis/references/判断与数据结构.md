# 判断与分析数据结构

## 从问题到知识需求

先明确决策，再列回答需要的知识。例如“每年电费”至少需要适用工况、实测/计算口径、运行时长和电价，额定功率只能支撑其中一部分。不能把“有某个关键词”当作知识充分，也不能从功率自动编造年耗电量。知识需求与验收条件是分析，不伪装成客户提供的事实。

不同报价对比时先列型号、配置、区域、有效期、税费、运输、币种和单位。无法确定同口径时说明可能冲突及条件不明；不通过文件名中的新旧自行裁决。案例、认证、价格或效果均照录来源，不认证真实性。

## 分析 JSON

字段名为稳定接口；内容默认中文。模板只展示一个问题，正式输入必须覆盖原始任务全部5—10个问题且保持顺序。

| 字段 | 含义/约束 |
|---|---|
| request_sha256 | manifest.json 中任务摘要，绑定企业、场景、问题原文 |
| reviewed_chunks | 实际读完全部审阅包后登记的全部片段id，不漏、不重 |
| questions[].id | 与输入问题id及顺序一致 |
| questions[].intent | 用户意图（分析） |
| requirements[].id | 同一问题内唯一 |
| key | 对象＋范围/条件＋知识点；跨问题同义需求同key，不跨型号/区域/年份合并 |
| knowledge | 具体所需知识，不能只写“更多信息” |
| criteria | 本需求充分覆盖的验收条件 |
| status | 充分/部分/缺失/冲突/无法判断 |
| rationale | 判断理由与尚缺信息；属于分析，不写入无来源企业事实 |
| evidence[] | 每条为 chunk_id 与 quote；quote 必须是该片段的连续原文 |
| search_terms | 缺失/无法判断时必填；记录实际检索的知识点与同义词，搜索仍不能代替全量审阅 |
| recommendation | 向谁补何资料、最少字段、可验收条件；已有充分资料可写“本项无需补充，保留来源” |
| priority | P0/P1/P2；充分项也填，表示该知识点在本问题的业务优先级 |
| confirmations | 待企业确认事项文本列表；有冲突必填 |

证据示例（仅结构演示，id和原文必须取本次实际语料）：

```json
{"chunk_id":"F000001:C000002","quote":"某文件中的连续原文"}
```

定位由脚本补齐，不能在 JSON 自填一个看似真实的页码来代替引用。Markdown/TXT按物理行，CSV按记录及结束物理行，DOCX按正文段落/表行列及附属部件，XLSX按工作表和单元格，PDF按页，PPTX按页和文本段/备注部件。长段落附字符范围，原文保持不改。

## 去重和可追溯边界

文件去重使用 SHA-256＋扩展名。相同字节、相同格式只解析一次；每个副本路径仍列清单，所有引文附副本路径。不按相似文件名或相似内容合并不同版本。

知识缺口按人工/Agent给出的 key 精确分组；脚本不会猜测同义词。不同 key 的语义同义去重仍需 Agent复核。共性缺口记录关联问题、最紧迫优先级和各补件建议。不把同内容副本计为冲突另一方或独立佐证。

## 自动校验能做什么

能检查结构、任务一致、审阅登记完整、原文字符串、来源树指纹、提取语料完整性及部分状态约束。不能判断 Agent 是否真的理解全部文本、引用是否语义充分、两个数值是否同口径冲突、企业事实是否真实，也不能自动核实一个去重key是否业务合理。最终交付须复核这些语义事项。
